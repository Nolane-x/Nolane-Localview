# Surface Owner Crash/Restart Reconciliation Design

## Status

Approved architectural direction for Phase D2 after D1 durable session identity continuity.

Base: `main` at `a12401397b7326bd453e99d4e255007c8bcaec32`.

Branch: `feat/d2-surface-owner-reconciliation`.

D1 established only logical `SessionId` continuity. D2 establishes live native-surface ownership continuity without allowing logical identity continuity to resurrect runtime authority.

## Goal

Make preview/workspace native surfaces converge correctly when either the LocalView daemon or the desktop owner crashes/restarts:

- a daemon restart may reuse the D1 `SessionId`, but every native-surface governor lease and owner authority is reacquired;
- a desktop process that survives a daemon restart may explicitly reattach its still-live platform surface under the new daemon boot;
- a desktop restart cannot inherit a predecessor process's surface authority merely because the same `SessionId`, label, or surface incarnation is reused;
- stale owner requests fail closed;
- abandoned owner state becomes explicit recovery debt rather than implicit live truth;
- cleanup is idempotent and returns resource accounting to baseline.

## Hard boundary inherited from D1

D1 guarantees only this:

> For an unambiguous durable lineage, the restarted daemon may rediscover the same logical target with the same committed `SessionId`.

D2 must not infer any of the following from that UUID:

- desktop owner liveness;
- native platform surface liveness;
- previous daemon resource leases;
- surface visibility;
- provider attachment;
- action authorization;
- evidence freshness;
- consequential authority.

`SessionId` is a logical identity reference. It is never an owner capability.

## Existing failure modes

### Daemon restart while desktop survives

Today the desktop can retain a Tauri/WebView surface and its local `DesktopSurfaceRegistry` entry while the daemon loses its in-memory `SurfaceResourceEntry` and governor lease. The next visibility update therefore sees two incompatible truths:

- desktop: platform surface exists and is owned;
- daemon: no live lease exists.

Blindly recreating the daemon lease from `SessionId` would turn identity continuity into authority continuity.

### Desktop crash while daemon survives

Today the daemon may retain a live `LiveResourceLease` after the desktop process that owned the native surface disappears. Because the lease is keyed by session/surface identity only, a later desktop process could collide with the stale logical owner or leave accounting above baseline.

### ABA across restarts

`DesktopSurfaceIdentity` currently uses `(SessionId, kind, label, incarnation)`. Incarnation is process-local desktop state. A fresh desktop process may begin again at incarnation `1`; therefore incarnation alone cannot distinguish the new owner from an old process that once owned the same logical surface.

## Selected architecture

D2 introduces four separate concepts:

1. `DesktopOwnerInstanceId` — cryptographically random UUID generated once per desktop process lifetime;
2. `DaemonBootEpoch` — cryptographically random UUID generated once per daemon process lifetime;
3. `OwnerLeaseId` — daemon-issued random capability created by owner registration and valid only inside one `DaemonBootEpoch`;
4. `SurfaceRecoveryDebt` — durable metadata recording that a live native surface had been activated but was not yet cleanly released before the previous daemon lifetime ended.

These values fence different dimensions and must not be collapsed into one identifier.

### DesktopOwnerInstanceId

Generated by the desktop process at startup and held only in process memory.

Properties:

- changes on every desktop process restart;
- stays stable while that desktop process survives a daemon restart;
- is not a user identity and is not persisted;
- is included in owner registration, surface reserve/activate/visibility/release, and reattach requests.

This closes desktop-process ABA.

### DaemonBootEpoch

Generated by the daemon at startup and held in process memory.

Properties:

- changes on every daemon restart;
- is returned by owner registration;
- is included in all later owner-authorized surface requests;
- a request carrying an old epoch is rejected even when every logical surface field matches.

This closes daemon-restart authority reuse.

### OwnerLeaseId

Registration creates a random UUID capability associated with:

```text
DesktopOwnerInstanceId
+ DaemonBootEpoch
```

The lease is process-local daemon state. It is never reconstructed from a durable journal.

Every mutating native-surface request must prove all three current values:

```text
owner_instance_id
boot_epoch
owner_lease_id
```

Possession of a current lease is the strong owner proof. A timeout is never proof that two owners are the same owner. Lease expiry may only revoke authority and trigger cleanup/debt handling.

### SurfaceRecoveryDebt

The daemon persists a bounded append-only recovery journal under the existing LocalView state root.

Conceptual events:

```text
Activated {
  session_id,
  surface_kind,
  label,
  incarnation,
  owner_instance_id
}
Released {
  same exact surface key + owner_instance_id
}
Reattached {
  same exact surface key + owner_instance_id
}
```

On daemon boot the journal is replayed into an inventory of outstanding activations. Replay creates **debt only**. It does not recreate an owner lease, governor lease, visibility, or platform-surface truth.

A surviving desktop process may discharge matching debt only by registering under the new boot epoch and presenting the same current `DesktopOwnerInstanceId` plus an exact surface identity through the reattach endpoint.

A new desktop process has a different `DesktopOwnerInstanceId`, so it cannot adopt predecessor debt.

## Control-plane protocol

### Register owner

`POST /v1/runtime/resources/surfaces/owners/register`

Request:

```json
{
  "owner_instance_id": "uuid"
}
```

Response:

```json
{
  "owner_instance_id": "uuid",
  "boot_epoch": "uuid",
  "owner_lease_id": "uuid",
  "recovery_required": true
}
```

Registration never proves a surface exists. It creates only current-boot owner authority.

Repeated registration by the same current desktop owner may replace its previous lease inside the same boot epoch; the replaced lease becomes invalid immediately. This makes registration deterministic and avoids parallel capabilities for one process instance.

### Reserve

Existing reserve requests gain:

```text
owner_instance_id
boot_epoch
owner_lease_id
```

Reservation keys include owner identity. A stale owner cannot cancel or consume another owner's pending reservation.

### Activate

Existing activate requests gain the same owner proof. After governor activation succeeds, the daemon appends durable `Activated` recovery debt before returning success. If durable debt recording fails, activation is rolled back and fails closed.

Publishing a successful surface activation therefore means both:

- the current boot has a fresh governor lease;
- abnormal daemon termination can later expose explicit recovery debt.

### Visibility

Visibility mutation requires exact current owner proof and exact live surface identity. Same session/label/incarnation from a stale owner is rejected as `surface_owner_fence_mismatch`.

### Release

Release requires exact current owner proof. The live governor lease is removed, then a durable `Released` event discharges debt. Release is idempotent for an exact owner/surface pair already known to be clean, but never treats a different owner as equivalent.

### Reattach after daemon restart

`POST /v1/runtime/resources/surfaces/reattach`

Request contains:

```text
session_id
surface_kind
label
incarnation
visibility
owner_instance_id
boot_epoch
owner_lease_id
```

Requirements:

1. current owner proof is valid;
2. D1 session currently exists;
3. outstanding recovery debt exists for the exact `(session, kind, label, incarnation, owner_instance_id)`;
4. no current-boot owner already controls the logical `(session, kind, label)`;
5. a fresh `NativeSurface` governor reservation is admitted and activated;
6. a durable `Reattached` event is appended;
7. only then is the current-boot live owner published.

Reattach never uses old governor state. It creates a fresh lease.

If no exact debt exists, the request fails closed. The desktop may then close/recreate the platform surface through the normal reserve/activate path.

## Owner liveness and cleanup

D2 adds an owner heartbeat endpoint bound to the owner lease.

The daemon tracks `last_seen` only as revocation input. Missing heartbeats may revoke an owner lease and release all current-boot live/pending resources for that owner. They do **not** establish the identity of a replacement owner and do not authorize reattachment.

A later process must register as a different owner instance and cannot adopt the expired owner's surfaces.

The first D2 slice uses a conservative bounded owner TTL of 15 seconds with a 5-second desktop heartbeat. Constants are internal and independently tested. This is a liveness revocation policy, not identity evidence.

## Desktop behavior

The desktop creates one `DesktopSurfaceOwner` at application startup containing `DesktopOwnerInstanceId` and current daemon registration.

Before reserve/activate/visibility/release:

1. ensure owner registration exists;
2. if the daemon reports an epoch mismatch or owner lease missing, register again;
3. for an already-existing platform surface, attempt exact reattach;
4. if exact reattach fails because debt is absent/mismatched, fail closed and recreate through normal lifecycle rather than fabricating adoption.

A daemon restart therefore becomes:

```text
existing platform WebView
+ same desktop owner instance
+ new daemon boot epoch
+ fresh owner lease
+ exact durable recovery debt
=> fresh governor lease + authoritative reattach
```

## Registry changes

`DesktopSurfaceIdentity` gains `owner_instance_id`.

The desktop registry continues to fence process-local incarnations but now validates owner identity as part of the full surface identity. A surface created by one desktop owner instance cannot be mutated by another owner instance even if all old logical fields match.

## Recovery journal requirements

The journal is deliberately narrower than full runtime persistence.

It contains no:

- governor budget/sample state;
- owner lease IDs;
- daemon boot epochs;
- visibility authority after restart;
- action/provider authority;
- evidence state.

Required durability properties:

- bounded event size;
- bounded replay count;
- `serde(deny_unknown_fields)` schema;
- UUID validation;
- exact owner/surface keying;
- append + flush before success for `Activated`, `Released`, and `Reattached` events;
- corruption fails closed and surfaces a diagnostic rather than being silently discarded.

Compaction is out of scope for the first D2 slice; the bounded journal may reject new activations when its configured maximum is reached rather than silently evicting recovery truth.

## Error semantics

New stable errors:

```text
surface_owner_not_registered
surface_owner_boot_epoch_mismatch
surface_owner_lease_mismatch
surface_owner_fence_mismatch
surface_recovery_debt_missing
surface_recovery_journal_unavailable
```

The caller may recover from registration/epoch errors by registering again. Fence/debt errors must not be automatically converted into ownership.

## Core invariants

D2 is complete only when tests demonstrate all of these:

1. same D1 `SessionId` across daemon restart does not preserve a live surface lease;
2. stale daemon boot epoch cannot mutate/release a current surface;
3. stale owner lease cannot mutate/release a current surface;
4. a new desktop owner instance cannot mutate/release predecessor state;
5. owner incarnation restart at `1` cannot ABA into predecessor authority;
6. reattach requires exact recovery debt and creates a fresh governor lease;
7. reattach with a different owner instance fails even when session/kind/label/incarnation match;
8. activation success is not returned until recovery debt is durably recorded;
9. release discharges exact debt and is idempotent for the same owner/surface;
10. expired owner cleanup returns pending/live governor accounting to baseline;
11. owner timeout is never used to infer replacement identity;
12. volatile/degraded D1 identity is never advertised by D2 as durable reattach continuity;
13. no provider/action/evidence authority is restored by any D2 path.

## Scope

In scope:

- owner-instance identity;
- daemon boot epoch;
- owner registration/heartbeat lease;
- owner-fenced reserve/activate/visibility/release;
- exact surface reattach;
- durable surface recovery debt journal;
- desktop owner integration;
- cleanup/revocation tests;
- exact restart tests and CI gate.

Out of scope:

- Perception Budget behavior changes;
- Windows UIA/provider ownership changes;
- consequential action authority;
- portal/capture provider reconciliation;
- full `Session` persistence;
- automatic adoption of ambiguous or volatile D1 sessions;
- cross-machine ownership.

## Rollout sequence

1. introduce pure owner-fence types and tests;
2. add current-boot owner registry and registration/heartbeat protocol;
3. fence current surface lifecycle requests;
4. add durable recovery journal and replay inventory;
5. add exact reattach path with fresh governor lease;
6. thread owner identity through desktop registry/resource client;
7. add daemon-restart and desktop-restart contract tests;
8. run whole-PR scope audit and exact-head CI/Windows UIA verification.
